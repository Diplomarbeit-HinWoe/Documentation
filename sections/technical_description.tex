\subsection{Overall Architecture}\label{sec:implementation:frontend:architecture}

\begin{figure}[htbp]
	\centering
	\includegraphics[width=1\textwidth]{pics/component-diagram.png}
	\caption{Component diagram of ArtAdmin. Source: \cite{aiComponentDiagram}}
	\label{fig:component-diagram}
\end{figure}

The component diagram \ref{fig:component-diagram} shows the overall architecture of ArtAdmin. The system is organized into four layers: the client applications layer, the identity and access management layer, the application layer, and the infrastructure service layer. This separation follows the principle of separation of concerns. The client application isolates the presentation layer from the business logic, while the identity and access management layer centralizes the single point of authentication. Furthermore, the infrastructure layer isolates the services that are needed to run this program. This design also allows for horizontal scaling of the backend, because it is stateless, meaning no information is saved directly within the REST application.

The client applications layer consists of a web application, which serves as the main user interface and handles the administration and display of users and information. It also includes ArtMeasure, a desktop application for calculating object measurements based on a 3D camera. Both applications communicate with the backend via a REST API over HTTP, and all user interfaces authenticate through the same OIDC provider, in this case Keycloak.

The application layer, or backend layer, consists of an ASP.NET Core backend, which is the core program handling all traffic and communicating with all services. Furthermore, this layer includes Pydantic Monty, a secure Python interpreter written in Rust for executing code generated by AI agents \cite{pydantic-monty}. This software is used to prevent ArtPilot from executing unauthorized and unsafe code while still enabling the import of any format.

This software solution uses four additional services, all of which can be self-hosted. For storing structured information, we use PostgreSQL. For image and vector data storage, we use MinIO, because it implements the S3 API and can therefore be replaced at any time by another program that also implements this API, such as AWS S3. Furthermore, for the use case of searching information, we use Elasticsearch, because it provides the speed and full-text search capabilities required. Redis is used as a cache for request results to speed up the application; it was chosen because it is a fast, in-memory key-value store, which is a widely used choice for this use case.

The comparison shows that all considered technologies are technically capable of implementing the ArtAdmin backend. Go and Quarkus achieve higher throughput in the selected TechEmpower benchmark, while Quarkus also provides advantages for applications that require very short startup times or a low memory footprint. However, these advantages are mainly relevant for serverless applications, edge deployments, or a large number of small services that are started frequently. ArtAdmin is designed as a long-running, containerized REST application. Its main workload consists of communication with PostgreSQL, MinIO, Elasticsearch, Redis, and Keycloak. Therefore, the maximum HTTP throughput of the framework is not the main limiting factor for the expected workload.

Quarkus was considered the main alternative to ASP.NET~Core because it is a modern Java framework with support for REST APIs, dependency injection, containerized development, and integrations for the required infrastructure services. The benchmark results show that Quarkus can achieve higher throughput than ASP.NET~Core in the selected test scenario. Nevertheless, the advantages of Quarkus in startup time and memory consumption are most significant when the application is compiled as a GraalVM native executable. Native compilation requires additional build time and may require explicit configuration of reflection and dynamic class loading \cite{quarkus-native-build,quarkus-native-tips}. These additional requirements are not necessary for ArtAdmin because the backend is intended to run continuously as a containerized service.

The developer team has experience in both Java and C\#. However, through a previous project and the focus of the previous school year, the team has more extensive practical knowledge of C\# and the .NET stack. This includes the development of REST APIs, database applications, Docker-based deployments, Kubernetes environments, and authentication with Keycloak, PostgreSQL, and Elasticsearch. By choosing C\#, the implementation risk was reduced, which allows the team to focus on project requirements such as the data model and other features. Existing skills and project-specific constraints are relevant factors when selecting a programming language ecosystem \cite{deldar2021ecosystemselection}. For these reasons, C\# was selected as the backend technology for this project. This decision does not imply that Quarkus, Go, or TypeScript-based frameworks are technically unsuitable, but in this use case, given the experience of the developer team, .NET is the best choice.


\subsection{Backend Architecture \cite{backend-architecture-language-cleanup}}\label{sec:implementation:backend:architecture}

This C\# backend solution is structured into seven separate projects. It was designed with the traditional ``N-Layer'' architecture in mind \cite{ms-common-web-architectures}. The ``N-Layer'' architecture, as Microsoft calls it, describes splitting an application into three layers: the user interface, the business logic, and the data access. This system follows this approach: the Persistence project is the data access layer, and the business logic is split into three different projects, namely Application, ArtVision, and Auth. The last layer is the user interface, which is represented by the ApiService, see Fig.~\ref{fig:backend-architecture}.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=1\textwidth]{pics/backend-layers.png}
	\caption{The layers of the backend. Source: \cite{claude_diagrams}}
	\label{fig:backend-architecture}
\end{figure}

The projects AppHost and Service Defaults do not contain use-case-specific code; they are configuration projects for Aspire.

The ArtAdmin.Persistence project contains the database entities, their configuration, the Entity Framework configuration, and the migrations. Furthermore, the database queries and persistence operations are encapsulated in the repositories of this project. This centralizes the database access for the entire system and reduces database-specific code.

The ArtAdmin.Application project contains the business logic of the application, where the information is prepared for the API. It is the central project of the backend and receives information from the ArtAdmin.Persistence, ArtAdmin.ArtVision, and ArtAdmin.Auth projects. Based on this data, it creates the DTOs that are sent to the API. This happens in the services defined in this project. The project also contains the DTOs with their validations and mappers, the startup initializer (to guarantee the functionality of the project, some data must be written to the database if it is empty), and the search logic.

The ArtAdmin.ArtVision project encapsulates the functionality related to the similarity search of the system. The feature extraction and the similarity search are defined in this project.

The ArtAdmin.Auth project encapsulates the entire authentication and authorization logic of the project. The connection to Keycloak is defined here, and the roles, groups, and user information are extracted for further use in the project, for example to secure the endpoints. This project also handles the user creation in Keycloak when a user is created through ArtAdmin.

The ArtAdmin.ApiService is the startup project of this solution. It exposes the backend functionality through HTTP endpoints. Its controllers handle the permissions and delegate the requests to the correct services. Furthermore, this project also handles the caching. This solution caches entire requests: if a request with the same parameters is sent again, it is not delegated to the services; instead, the already calculated information is sent to the client.

Based on the comparison, the Intel RealSense D456 was selected
for the system. The main reason was the open-source librealsense
SDK, which provides example applications for working with the
camera data. These examples helped with the development of the
desktop application. The SDK also includes an example for
measuring the distance between two points in three-dimensional
space \cite{rs_sdk}.

Software integration was an important part of the decision.
The table includes other devices with open-source SDKs, so this
was not the only factor considered. The specified working
distance of up to 6\,m was another reason for choosing the D456
\cite{rs_specs}. However, the relevance of this range depends
on the size of the objects and the distance between the camera
and the object during measurement.

The comparison also shows some limitations. Several scanners
list smaller accuracy values, but these values describe
different metrics and measurement conditions. They cannot
be used on their own to decide which device is most suitable
for the application. The D456 was therefore selected mainly
for its software integration and working range, rather than
for having the best reported accuracy.

The manufacturer's specifications do not show how accurately
the completed system can measure object dimensions. Practical
tests are needed to evaluate the measurement results and
determine whether they meet the requirements of the application.
